Incident retrospective · Flatiron Health

Ten million PDFs to fix

Editing a PDF left every previous version of the document inside the file, and a user noticed. I built the system that replaced affected documents at roughly a million files an hour, designed so that no document could ever be lost.

Detection

A user saw data that should have been gone

  • A user reported seeing data they weren't expecting in their document, and that report surfaced the problem
  • Editing a PDF created a new version of the document inside the same file. The previous version was never removed, so deleted data was still present.
  • Most PDF readers never display the earlier versions, so the leftover data was invisible in normal use
  • The company stored more than 100 million files of this type

Triage

Three groups working in parallel

The company split the response into three groups. I was assigned the third on a Thursday, mid-day.

Hide

  • Hide potentially affected files from users until resolution

Identify

  • Scan the 100M+ stored documents and publish lists of potentially affected files

Fix · mine

  • Replace every listed document with a corrected copy, quickly and safely

The brief for my group: given parquet files listing potentially affected documents, replace them with corrected files, fast, with zero data loss

Resolution · safety

Every document had a way back

  • A backup copy landed in S3 before any document was touched
  • The original was overwritten only after its fix succeeded
  • Errors were retried, and repeated failures went to a dead-letter queue for manual follow-up
  • Updates were confirmed through logs

Resolution · the fix

No library fixed every document

  • Documents ran through two processing approaches, because neither one succeeded on every file
  • I extracted the functionality I needed from one library and combined it with a second, which together fixed almost 100% of the affected documents

Challenges

What made it interesting

  • Super high visibility and impact
